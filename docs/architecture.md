# Архитектура

## Границы Sprint 1

Вертикальный срез доказывает путь `браузер → Socket.IO → сервер → все браузеры`: игрок создаёт комнату, второй входит по коду, оба видят общий список и серверно подтверждённые координаты на Phaser-карте.

```text
React (лобби и HUD) ─┐
                     ├─ client ── Socket.IO ── server
Phaser (карта) ──────┘                         ├─ RoomStore
                                              ├─ валидация
shared (типы, события, карта) ─────────────────┘
```

## Пакеты monorepo

- `client/` — React отвечает за страницы и состояние интерфейса; Phaser рисует мир и считывает ввод.
- `server/` — Express предоставляет `/health`; Socket.IO обслуживает комнаты и движение; `RoomStore` хранит состояние в памяти.
- `shared/` — единственный источник TypeScript-контрактов, имён событий и геометрии карты.

## Поток движения

1. Phaser с частотой не выше 20 раз/с отправляет направления клавиш, а не координаты.
2. Сервер проверяет payload, ограничивает интервал времени и вычисляет допустимое смещение.
3. Сервер ограничивает границы и не пропускает окружность игрока через препятствия.
4. Сервер рассылает снимок комнаты; клиенты плавно перемещают спрайты к подтверждённым координатам.

Это базовая authoritative-модель. Клиентская интерполяция есть, prediction/reconciliation оставлены на следующий этап.

## Состояние и масштабирование

Комнаты живут в `Map` одного процесса и исчезают после перезапуска. Для MVP это уменьшает сложность. Для нескольких процессов понадобятся внешний адаптер Socket.IO, постоянное или распределённое хранилище и механизм сессий/переподключения.

## Правила расширения

- игровые решения принимает сервер;
- секретные роли никогда не входят в публичный `RoomState`;
- сначала меняются `shared` и `docs/socket-events.md`, затем клиент и сервер;
- обработчики транспорта не должны содержать всю игровую логику — она переносится в тестируемые сервисы;
- любые новые действия проверяют членство, фазу, право, дистанцию и повторное выполнение.
