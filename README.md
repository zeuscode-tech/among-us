# Among Us — учебная браузерная multiplayer-игра

Учебный командный проект: браузерная 2D-игра для 4–10 участников по основным механикам Among Us. Игроки входят в комнату по коду, получают секретные роли, выполняют задания, сообщают о найденных телах и голосуют. Предатели пытаются устранить экипаж, не раскрыв себя.

> Проект создаётся в образовательных целях и не связан с Innersloth. Название Among Us и связанные товарные знаки принадлежат их правообладателям. Для публичного релиза следует использовать собственное название, карту, графику и звуки.

## 1. Цель и состав MVP

Цель — за 14 дней получить демонстрируемый сетевой MVP, в котором можно провести полный матч от лобби до объявления победителя.

MVP включает:

- создание комнаты и подключение по короткому коду;
- лобби, список игроков и запуск хостом;
- 4–10 игроков в одной комнате;
- 1 предателя при 4–6 игроках и 2 при 7–10;
- одну 2D-карту со стенами и коллизиями;
- сетевое перемещение в реальном времени;
- минимум два простых типа заданий и общий прогресс;
- убийство с проверкой дистанции и перезарядкой;
- тело, репорт, обсуждение и голосование;
- автоматическую проверку условий победы;
- обработку отключения игрока;
- экраны победы и поражения и возврат в лобби.

## 2. Стек

| Область | Технология | Назначение |

| Интерфейс | React + Vite + TypeScript | Главная, лобби, HUD, голосование, результаты |
| 2D-игра | Phaser + TypeScript | Карта, персонажи, камера, управление, коллизии |
| Сервер | Node.js + Express + TypeScript | HTTP и серверная игровая логика |
| Realtime | Socket.IO | Комнаты, команды и синхронизация состояния |
| Данные MVP | Map в памяти процесса | Комнаты, игроки и матчи без базы данных |
| Контракты | Общие TypeScript-типы | Одинаковые структуры на клиенте и сервере |
| Дизайн | Figma | Карта, интерфейс и собственные ассеты |
| Работа команды | GitHub Issues, Projects и Pull Requests | Задачи, ревью и история вклада |

Один язык на клиенте, сервере и в общих контрактах уменьшает количество несовместимых решений и ускоряет параллельную работу.

## 3. Архитектура

    React UI ─┐
              ├─ Browser client ── Socket.IO ── Node.js authoritative server
    Phaser ───┘                                      │
                                                     ├─ Room manager
                                                     ├─ Game state machine
                                                     ├─ Action validators
                                                     └─ Win-condition checker

Клиент считывает ввод, рисует подтверждённое состояние, сглаживает движение и отправляет намерения игрока. Сервер создаёт комнаты, хранит каноническое состояние, распределяет роли и задания, проверяет действия, переключает фазы lobby → playing → meeting → voting → ended и определяет победителя.

## 4. Правила безопасности сервера

Главный принцип: **сервер — единственный источник истины**. Клиент не сообщает готовый результат, а запрашивает действие; сервер принимает или отклоняет его.

Обязательные правила:

- игрок связывается с текущим socket.id или безопасным токеном сессии;
- все payload проверяются по типу, длине и допустимым значениям;
- клиент не назначает себе роль, координаты, состояние жизни или победу;
- сервер ограничивает скорость и запрещает телепортацию и проход сквозь стены;
- убийство доступно только живому предателю в фазе игры, рядом с живой целью и после cooldown;
- задание завершает только назначенный живой игрок у нужной точки и только один раз;
- репорт доступен только рядом с существующим неотмеченным телом;
- голос принимает сервер только от живого игрока, в нужной фазе и один раз;
- игру запускает только хост при допустимом числе игроков;
- роль и персональные задания отправляются только конкретному сокету;
- публичное состояние не содержит ролей живых игроков;
- частота движения и интеракций ограничивается;
- имена и коды комнат имеют лимит длины и допустимые символы;
- клиент получает безопасный код ошибки без серверного stack trace;
- после значимых действий повторно проверяются условия победы;
- отключение игрока не должно оставлять матч в зависшем состоянии.

В MVP данные исчезают после перезапуска сервера. Для реального публичного запуска понадобятся постоянное хранилище, аутентификация, наблюдаемость, защита от злоупотреблений и нагрузочное тестирование.

## 6. Функции

### Лобби

- создать комнату и получить код;
- войти по коду с уникальным именем;
- видеть список и готовность игроков;
- передать роль хоста при его отключении;
- запретить вход после старта;
- запустить матч только при 4–10 игроках.

### Матч

- движение WASD или стрелками, камера и коллизии;
- синхронизация с ограниченной частотой обновлений;
- точки взаимодействия и подсказки;
- персональные задания и командная шкала;
- убийство, cooldown и тело;
- репорт и остановка игрового движения;
- обсуждение 45 секунд и голосование 30 секунд;
- голос за игрока или Skip;
- исключение, ничья и возврат на карту;
- победа по заданиям, исключению предателей или численному перевесу;
- финальный экран с результатом и раскрытием ролей.

### Технические функции

- общие TypeScript-типы;
- структурированные ошибки;
- GET /health для проверки сервера;
- базовые серверные логи;
- URL сервера через переменные окружения;
- unit-тесты валидаторов и условий победы;
- smoke-test матча в нескольких браузерах.

## 7. Сценарий матча

1. Игрок создаёт комнату и получает код, например ABCD12.
2. Остальные входят; хост видит список и запускает матч.
3. Сервер случайно выбирает 1 или 2 предателей и лично сообщает каждому его роль.
4. Мирным назначаются задания, все появляются в стартовой комнате.
5. Экипаж выполняет задания; предатели могут убить ближайшего игрока после 20-секундного cooldown.
6. Живой игрок находит тело и отправляет репорт. Сервер замораживает движение.
7. После 45 секунд обсуждения начинается 30-секундное голосование.
8. Сервер исключает лидера. При ничьей или победе Skip никто не исключается.
9. Если условия победы не выполнены, начинается следующий раунд.
10. Экипаж выигрывает после исключения всех предателей или завершения обязательных заданий. Предатели выигрывают, когда живых предателей не меньше, чем живых членов экипажа.

Убитые игроки в MVP не голосуют и не общаются с живыми через интерфейс. Их незавершённые задания исключаются из обязательного общего количества. Призраки остаются за пределами MVP.

## 9. События Socket.IO

До параллельной разработки команда фиксирует payload, ответ, ошибки, разрешённую фазу и адресатов каждого события.

### Клиент → сервер

| Событие | Назначение | Проверки |
|---|---|---|
| room:create | Создать комнату | имя и лимит комнат |
| room:join | Войти по коду | существование, место, фаза lobby |
| room:leave | Выйти | членство в комнате |
| player:ready | Изменить готовность | только свой статус |
| game:start | Запустить матч | хост и 4–10 игроков |
| player:move | Передать ввод | скорость, частота, фаза, коллизии |
| task:interact | Начать задание | владелец, дистанция, фаза |
| task:complete | Завершить задание | назначение, повтор, дистанция |
| player:kill | Попытка убийства | роль, жизнь, дистанция, cooldown |
| body:report | Репорт тела | существование тела и дистанция |
| vote:cast | Голос или Skip | фаза, право голоса, один раз |

### Сервер → клиент

| Событие | Назначение | Адресат |
|---|---|---|
| room:state | Публичное состояние лобби | комната |
| game:started | Старт и публичные параметры | комната |
| player:private-state | Роль и задания | один игрок |
| game:snapshot | Подтверждённый мир | комната |
| player:joined / player:left | Состав | комната |
| task:progress | Общий прогресс | комната |
| meeting:started | Репорт и таймер | комната |
| voting:started | Голосование и дедлайн | комната |
| vote:result | Итог | комната |
| game:ended | Победитель, причина, роли | комната |
| action:rejected | Безопасная ошибка | инициатор |

Клиентские команды получают acknowledgment с полями ok, errorCode и нужными данными.

## 11. Git-процесс

1. Ветка main всегда должна собираться и запускаться.
2. После начала командной работы прямые изменения в main запрещены.
3. Одна Issue — одна небольшая ветка: feature/lobby, feature/player-movement или fix/double-vote.
4. Перед стартом участник назначает Issue на себя и переводит её в In Progress.
5. Коммиты понятны: feat: add room creation, fix: reject duplicate vote, docs: describe socket events.
6. PR содержит ссылку на Issue, описание, способ проверки и скриншот для визуальных изменений.
7. Нужен минимум один reviewer; изменения контрактов проверяет Tech Lead или Backend/Realtime-разработчик.
8. Автор обновляет ветку от main, устраняет конфликт и проверяет сборку.
9. Используется squash merge: одна задача превращается в один понятный коммит.
10. GitHub Project имеет колонки Todo, In Progress, Review, Done.

Сначала согласуются документация и общие типы, затем меняются клиент и сервер.

## 13. Критерии приёмки

MVP готов, если:

- 4–10 клиентов входят в одну комнату с разных браузеров или устройств;
- только хост запускает матч, сервер проверяет число игроков;
- роли распределяются корректно и не попадают в публичное состояние;
- движение синхронизируется, скорость ограничена, стены работают;
- есть минимум два задания и серверный общий прогресс;
- убийство возможно только для допустимой цели рядом и после cooldown;
- тело репортится один раз и запускает встречу;
- живой игрок голосует не более одного раза, мёртвый не голосует;
- ничья и Skip работают по правилам;
- обе стороны могут победить каждым предусмотренным способом;
- отключение одного игрока не зависает матч;
- клиент не может назначить роль, завершить чужое задание, голосовать дважды или убить на расстоянии;
- проект запускается по README, публичная демонстрация проходит полный матч;
- вклад каждого участника виден в Issues и Pull Requests.

## 14. Ограничения MVP

В первую версию не входят:

- аккаунты, регистрация и база данных;
- матчмейкинг, публичный список комнат и рейтинг;
- несколько карт и редактор уровней;
- сложные саботажи, вентиляция и камеры;
- голосовой или текстовый чат;
- полноценные призраки;
- косметика, магазин, платежи и достижения;
- мобильное сенсорное управление;
- промышленный античит и горизонтальное масштабирование;
- копирование оригинальной графики, аудио, карты или брендинга.

## 15. Демонстрация и защита

На защите команда проводит короткий матч минимум в четырёх окнах: показывает вход по коду, роли, движение, задание, убийство, репорт, голосование и победу. Затем каждый участник за 1–2 минуты объясняет свой модуль и показывает связанную Issue или Pull Request.

Главный показатель успеха — полный, проверяемый и устойчивый сетевой игровой цикл, а не количество декоративных эффектов.
